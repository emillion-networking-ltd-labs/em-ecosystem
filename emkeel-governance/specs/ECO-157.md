# ECO-157 — design-propagation Fase 1 (E4c): VRT por consumidor como guardia de propagación required + endurecer marcadores de conflicto + red de flake

Strategy: design-propagation

## Resumen

Tercer y último entregable de **E4 (rollout safety)** de la estrategia **design-propagation** (ADR-028,
build-now item 4), que **cierra E4** (y la Fase 1). Promueve el VRT propio de cada satélite (Playwright visual +
a11y, hoy `required: false`) a **guardia de propagación REQUIRED**: un update del design-system no puede aterrizar
roto (visual o de accesibilidad) sobre un consumidor. Reusa `hold` de E4a como freeze y **no** reconstruye nada
de E4a/E4b.

**El insight que da forma al scope:** el reporter de flota de E4b (`_manifest.mjs`) es un clasificador PURO,
byte-only, sin navegador, **pull-only**, que corre en OTRO workflow (`em-ui-governance.yml`) que el VRT
(`visual-regression.yml`) y sin estado compartido. Por eso "VRT-fail se suma al conjunto rojo del reporter"
(ECO-155) se realiza en la **capa de check REQUIRED** (un agregador de nombre estático que la branch protection
exige), **NO** acoplando el core byte-puro a un artefacto de VRT. Se preserva el invariante PULL: la guardia solo
**OBSERVA** (renderiza las páginas committeadas del consumidor contra su baseline committeado) y **BLOQUEA**;
jamás empuja ni escribe bytes en un consumidor.

Piezas:

- **D1 — VRT de satélite always-run + green-skip** (`visual-regression.yml`): el job corre en CADA PR (para
  reportar un status requerible); los pasos pesados hacen green-skip cuando el PR no toca satélites (patrón
  ECO-38 del dashboard) → pata SUCCESS sin bloquear PRs ajenas.
- **D2 — agregador de nombre estático** (`Satellite visual regression (all)`): `needs:` el matrix, `if: always()`,
  **FAIL-ONLY** (falla en failure/cancelled, pasa en success **Y** skipped — fleet vacía → matrix skipped → no
  bloquear). Un context estático cubre las patas dinámicas del matrix (`Satellite visual regression (satellites/…)`,
  que NO se requieren por ser dinámicas).
- **Endurecer CONFLICTO** (`conflict-markers.yml`, always-run, sin paths-filter): hace REQUIRED el subconjunto
  determinista-y-duro (un marcador de conflicto git rompe el build). Corrige la inversión de fiabilidad de
  endurecer solo la señal flaky (VRT) mientras la fiable (marcadores) queda advisory.
- **Red de flake** (`playwright.config.ts` del satélite): la política que hace seguro requerir un check visual
  flaky YA existía y se documenta como tal — `retries: 2` en CI + `maxDiffPixelRatio: 0.002` + `animations:
  "disabled"`. Un fallo que persiste tras 2 retries es una regresión real.
- **D3 — wiring de required** (`check-branch-protection.mjs` EXPECTED.contexts + tests): añade
  `Satellite visual regression (all)` y `Conflict markers` al intent + fixtures.

## Decisiones fijadas (operador)

- **Required AHORA** (con la red de flake): E4c completo en un ticket. La red de flake (retries + umbral +
  animations off, ya presente) desactiva el riesgo de falsos bloqueos que haría prematuro el flip.
- **Endurecer el subconjunto CONFLICTO a required** (no solo el VRT): la señal determinista más dura también
  bloquea, no solo avisa.
- **Reporter de flota se queda BYTE-PURO** (D5, reinterpretación ratificada): "VRT-fail = rojo" se realiza en la
  capa de check required (el agregador), NO leyendo VRT desde `_manifest.mjs` (un fichero de status committeado
  sería a su vez gobernado/drift-prone, y acoplar el core pull-only a un artefacto de navegador rompe su pureza).
  El "rojo" que ve el operador es la UNIÓN de (a) el reporter byte/manifest advisory y (b) la guardia VRT
  required. Cross-link con la frase de ECO-155 para que las specs no se contradigan.
- **O2/O3 no son forks reales** (documentados): requerir los nombres per-satélite del matrix es inseguro (son
  dinámicos → required-context ausente bloquearía todo PR) → se requiere solo el agregador estático. Y `hold` es
  ORTOGONAL al VRT (el VRT compara estado committeado, no corre `em-ui update`) → no hay interacción hold↔VRT que
  construir; un update congelado por `hold` simplemente no cambia la página, así que su VRT sigue verde solo.

## Acceptance Criteria

- El job del VRT de satélite reporta un status en **CADA PR** a main; en un PR que NO toca satélites, los pasos
  pesados hacen green-skip y la(s) pata(s) terminan **SUCCESS** (no se malgastan runs ni se bloquean PRs ajenas).
- El agregador `Satellite visual regression (all)` es **FAIL-ONLY**: falla si alguna pata es failure/cancelled;
  pasa en success **y** en skipped (fleet vacía / matrix omitido) — nunca brickea main.
- `conflict-markers.yml` corre en cada PR (sin paths-filter) y falla si hay marcadores de conflicto en cualquier
  árbol; su check `Conflict markers` es requerible.
- `check-branch-protection.mjs` declara `Satellite visual regression (all)` y `Conflict markers` como required en
  `EXPECTED.contexts` (strict:true), y los self-tests (`node --test`) pasan.
- El reporter de flota de E4b (`_manifest.mjs`, `check-fleet-report.mjs`, `cli.mjs report`) **NO cambia** — se
  preserva su pureza byte/pull-only; "VRT-fail = rojo" vive en la capa de check required.
- La red de flake del VRT required está documentada (retries + umbral + animations off).
- **Ships con tests** de la lógica pura de required (los self-tests de `check-branch-protection`).

### Runbooks

- **D4 — flip real a required (acción admin del operador, tras el merge):** `check-branch-protection.mjs` solo
  DETECTA deriva (weekly-audit); NO aplica. Para que el bloqueo sea efectivo, un admin debe parchear la branch
  protection viva de `main` con los 2 contexts nuevos. El propio gate imprime el comando `gh api -X PATCH
  repos/<repo>/branches/main/protection/required_status_checks -F strict=true -f 'contexts[]=…'` con TODOS los
  EXPECTED. **Hasta aplicarlo, el intent+tests están verdes pero el merge NO está realmente bloqueado**, y el
  weekly-audit marcará la deriva — aplicarlo pronto tras el merge.
- **Onboarding de un satélite nuevo (bajo la guardia required):** su 1er PR toca `satellites/**` → su pata corre
  el VRT REAL, pero aún no tiene baseline committeado → `toHaveScreenshot` escribiría el baseline Y fallaría → el
  agregador required bloquearía el PR que lo introduce. **Runbook:** capturar el baseline ANTES del PR vía
  `gh workflow run visual-regression.yml --ref <rama> -f capture_baseline=true -f baseline_ref=<rama> -f
  package=satellite` (el workflow empuja el baseline a la rama), o committear los baselines en el PR de
  onboarding.
- **Re-run de un flake genuino:** re-lanzar el job del VRT de satélite (los `retries: 2` ya absorben la mayoría);
  si persiste, reproducir con el baseline_ref del PR y regenerar el baseline si el cambio visual es intencional
  (mismo mecanismo que ECO-153).

## Alignment

Implementa/toca estas decisiones del norte de `design-propagation` (ADR-028):

- **Rollout safety — VRT por consumidor como guardia (build-now item 4)**: E4c es la 3ª y última pieza del
  mecanismo E4; hace del VRT propio de cada satélite una guardia REQUIRED que impide que un update aterrice roto.
  Cierra E4 (y la Fase 1).
- **Halt-on-red**: el "rojo" que detiene una propagación se hace enforcing en la capa de check required (agregador
  VRT + marcadores de conflicto), complementando el reporter advisory de E4b.
- **Invariante PULL preservado (hard, ADR-006/007/027)**: la guardia solo OBSERVA (renderiza estado committeado
  vs baseline committeado) y BLOQUEA; no empuja ni escribe bytes. El reporter byte-puro no se acopla a VRT.
- **`hold` de E4a como freeze de rollout**: reusado sin código nuevo — `hold` congela bytes, así que una página
  congelada no cambia y su VRT sigue verde (ortogonal al VRT, que nunca corre `update`).
- **2 clases de error**: se endurece a required tanto la señal fuzzy (VRT visual/a11y) como la determinista
  (marcadores de conflicto), evitando la inversión de fiabilidad.
- **No-goals respetados**: no hay pusher central, no se auto-remedia/auto-back-porta un consumidor roto (la
  guardia observa/bloquea/congela, nunca reescribe), no se acopla el core byte-puro a un artefacto de navegador,
  no se requieren los nombres dinámicos del matrix.
