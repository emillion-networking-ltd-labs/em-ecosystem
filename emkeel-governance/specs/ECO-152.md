# ECO-152 — design-propagation Fase 1 (E4a): manifest por-consumidor (SHA base por fichero) + verbos `pin`/`hold`/`unhold` + gate `check-manifest`

Strategy: design-propagation

## Resumen

Primer entregable de **E4 (rollout safety)** de la estrategia **design-propagation** (aprobada, ADR-028). El
CLI `em-ui` propaga el design-system a los consumidores (dashboard + satélites) por copia literal, pero era
**stateless**: nada registra de QUÉ revisión de la fuente venía cada copia. Sin eso no se puede distinguir una
copia stale de una al día, no hay base sobre la que anclar un reconcile asistido futuro, ni forma de **congelar**
a propósito el fichero de un consumidor. E4a añade esa capa de estado por-consumidor — el mínimo que desbloquea
E4b (reporter de flota) y E4c (VRT por consumidor) sin construir todavía la máquina de merge.

Se construyen 5 piezas (todas node stdlib puro, ethos lib+shell como ECO-144):

- **`_manifest.mjs`** (lib pura nueva, hermana de `_reconcile.mjs`): `blobSha(buf)` = git blob SHA-1 in-process
  vía `node:crypto` **sobre BYTES** (`Buffer.length`, no `String.length`) — idéntico a `git hash-object`, sin
  shell a git (funciona en checkout shallow); `destRelFor` (única fuente de verdad del mapeo fuente→clave,
  compartida con `cli.destPathFor`); `governedSources`, `isHeld`, `readManifest`/`writeManifest`/`recordEntry`/
  `validateManifest` (los helpers con IO, COMPARTIDOS por CLI y gate para que nunca discrepen).
- **Manifest por-consumidor** `<src>/em-ui.manifest.json`: `{version, source, files: { "<dest-rel>": { from, sha,
  hold? } }}`. Clave = ruta relativa al consumidor (el resultado de `destRelFor`); `from` = ruta fuente del DS;
  `sha` = blob SHA-1 de la fuente al copiarse (la BASE); `hold` opcional = congelado.
- **`add`/`update`/`init` hacen upsert** del manifest por cada fichero que copian/adoptan; se persiste UNA vez al
  final (transaccional). `update` **respeta `hold`** (lo salta, benigno, exit 0) y **preserva intacto** el valve
  `@em-ui-adapted` (sigue saliendo con código 3 cuando protege una adaptación).
- **Verbos `pin`/`hold`/`unhold`**: `pin <C>` fija la base al blob-sha actual del DS sin copiar bytes; `pin all`
  re-baselinea todas las copias presentes (el productor del bootstrap); `hold`/`unhold <C>` congela/descongela.
- **`check-manifest.mjs`** (gate bloqueante nuevo, en las cadenas `governance`+`coverage`): valida completitud
  (source-driven) e integridad del manifest de cada consumidor; fail-closed. `check-component-drift` aprende a
  **eximir** las copias en `hold` (como ya exime `@em-ui-adapted`).

Se **generan y committean** los manifests iniciales de los 2 consumidores existentes (dashboard 57 entradas,
sat-cristian-garcia 20) con `em-ui pin all` — el gate es fail-closed, no pueden quedar sin manifest.

## Decisiones fijadas

- **`sha` = git blob SHA-1 de la fuente, byte-exacto** (no commit-SHA, no semver). Content-addressable. **Se
  computa sobre `Buffer.length` (BYTES), jamás `String.length`**: las fuentes del DS tienen multibyte (acentos);
  un header `blob <chars>\0` daría un sha que NO casa con git y desalinearía en silencio cada fichero acentuado.
  Verificado contra `git hash-object` incl. AlertBox (2103 bytes ≠ 2090 chars).
- **Granularidad de `pin`/`hold <C>`: SOLO el fichero PROPIO del componente** (`item.file`), NO su closure ni sus
  `internalDependencies` compartidas. `lib/utils.ts` lo tiran N componentes; congelar/re-pinear una dep
  compartida vía un componente afectaría en silencio a todos los demás. Para operar sobre todo el consumidor,
  `pin all` / `hold all` (explícito).
- **`hold` es ortogonal a `@em-ui-adapted`**: `hold` = freeze de rollout (update lo salta, benigno, exit 0);
  `@em-ui-adapted` = adaptación protegida (update sale con código 3). Los marcadores de conflicto ganan a ambos.
- **Manifest en la raíz `<src>` del consumidor** (`--dest`) — el único handle que el CLI tiene sobre un
  consumidor. Decisión consciente; moverlo a la raíz del paquete sería una migración futura.
- **Scope mínimo-forward**: solo el manifest, los 3 verbos y el gate. NO `baseBlob` store, NO pin por-commit, NO
  `git merge-file`/`adopt`/`--continue` (la máquina de merge se difiere a E4b). La capa de marca templada
  (`em-ui-brand.css`, `__BRAND__`-substituida, no copia literal) queda fuera del manifest.
- **Test de integración en `design-system/tests/`** (vitest, shellea el CLI real), el home de tests del repo y
  el precedente de ECO-144 — no un `tests/integration/` de raíz (`check_critical_integration` es emkeel-scoped,
  N/A en este repo; verificado en el fuente del gate).

## Acceptance Criteria

- Cada consumidor con copias gobernadas lleva `<src>/em-ui.manifest.json` que registra, por copia, la fuente del
  DS (`from`) y el **git blob SHA-1 byte-exacto** de esa fuente (`sha`, casa con `git hash-object`).
- `em-ui add`/`update`/`init` **crean o refrescan** (upsert) las entradas del manifest de los ficheros que
  copian/adoptan, persistiendo el manifest una vez al final.
- `em-ui pin <C>` fija la base del fichero propio de C sin copiar bytes; `em-ui pin all` re-baselinea todas las
  copias presentes; `hold <C>`/`unhold <C>` marcan/desmarcan `hold`. `pin`/`hold <C>` afectan **solo** al fichero
  propio de C, no a sus dependencias compartidas.
- `em-ui update` **salta** un fichero en `hold` (no lo clobbea; sale con código 0) y **preserva intacto** el
  comportamiento `@em-ui-adapted` (sigue saliendo con código 3 al proteger una adaptación).
- El gate **`check-manifest`** falla CI (código ≠0) cuando un consumidor con copias gobernadas no tiene manifest,
  una copia presente no tiene entrada, o una entrada tiene `from` no-fuente / clave ≠ mapeo / sha no-40-hex /
  fichero destino inexistente. Corre en las cadenas `governance` y `coverage` y en PRs de rutas de consumidor.
- `check-component-drift` **exime** las copias marcadas `hold` (como exime `@em-ui-adapted`); los marcadores de
  conflicto siguen fallando por encima de toda exención.
- Los 2 consumidores existentes shippean su manifest inicial (generado con `em-ui pin all`), así el gate
  fail-closed no enrojece ningún PR de consumidor.
- Ships con **test de integración** (`design-system/tests/manifest.test.ts`) que ejercita
  add→manifest→hold→update-skip→unhold→gate end-to-end + el cross-check del blob-sha contra `git hash-object`.

## Alignment

Implementa/toca estas decisiones del norte de `design-propagation` (ADR-028):

- **Rollout safety / propagar a N sin romper (estrategia L138, ADR-028:38)**: el manifest es la primera pieza del
  mecanismo E4 — la base de SHA por fichero que permite a la flota razonar sobre "¿esta copia está al día?".
  Concreta la pieza de manifest que E1/ECO-144 **difirió explícitamente** a esta fase.
- **Reconcile base-pinned (build-now)**: el `sha` por fichero es la BASE que el reconcile asistido de E4b
  (`git merge-file`) leerá; E4a la registra sin construir todavía la máquina de merge (mínimo-ahora, resto gated).
- **Invariante PULL preservado (hard, ADR-006/007/027, re-ratificado ADR-028:36)**: `pin`/`hold`/`update` operan
  sobre el árbol PROPIO del consumidor vía `--dest`; ningún actor central empuja bytes ni escribe manifests ajenos.
- **Dos clases de error — crudo grep-catchable vs semántico (ADR-028)**: `check-manifest` es un gate determinista
  y grep-catchable (completitud/integridad del manifest), complementario a `check-component-drift` (drift de bytes).
- **Freeze declarado por-elemento**: `hold` extiende el modelo de divergencia consciente por-elemento (junto a
  `@em-ui-adapted`) hacia el freeze de rollout que E4c usará como guardia de propagación.
- **No-goals respetados**: no revive DTCG, no hay generador que empuje, no se re-plataforma em-ui, no se toca el
  contrato de ningún primitivo registrado, no se construye la máquina de merge (diferida a E4b).
