# ECO-176 — Storybook: "Composed of" auto-derivado + norma de clasificación

Strategy: design-system-quality

## Contexto

Con el sidebar en Simple/Composite (ECO-175), un compuesto debería DECIR de qué se compone — como referencia
navegable, para hacer visible la propagación (SegmentedControl → Button = "sigue a Button"). La clave: leerlo
del REGISTRY (`registryDependencies`), no escribirlo a mano (driftaría).

## Alcance

- **Decorator `withComposedOf`** (preview.tsx): para las stories `Composite/*`, muestra un chip
  **"Composed of: <primitivos>"** leído de `registry.json` (`registryDependencies`). Auto para todas, cero
  código por-story, no puede driftar ni olvidarse. Los `Simple/*` (hojas) no muestran banner.
- **Norma `check-composition-class.mjs`** (encadenada en `npm run coverage`): una pieza `Composite/*` DEBE
  tener `registryDependencies` no vacío (compone primitivos de verdad). NO se enforce la dirección Simple —
  un primitivo puede usar un helper interno (Button usa SpinnerInfinity para el spinner de carga) y seguir
  siendo el primitivo de referencia; "compuesto" es *hecho de otros primitivos como esencia*, un juicio.

## No-goals

- No es el detector de DUPLICACIÓN del censo (el que caza "re-implementa un primitivo en vez de componerlo",
  el caso SegmentedControl previo) — ese es aparte y más fuerte. Esta guarda solo verifica que un Composite
  compone de verdad.

## Acceptance Criteria

- Las stories `Composite/*` muestran "Composed of: <deps>" derivado del registry; los `Simple/*` no.
- `check-composition-class` en `coverage`: verde con SegmentedControl (compone Button); falla si un Composite
  no compone nada.
- coverage + story-norm + tsc verdes; Storybook build verde.

## Alignment

- **Reuso de primitivos (single source):** el grafo de composición vive en el registry; el catálogo lo MUESTRA
  y una guarda lo VERIFICA — nada escrito a mano, nada que driftar.
