# ECO-158 — design-propagation: máquina de reconciliación asistida (git merge-file 3-way base-pinned)

Strategy: design-propagation

## Resumen

El **item 1** de la estrategia design-propagation (build-now): la reconciliación base-pinned que permite a un
consumidor **conservar su adaptación `@em-ui-adapted` Y recibir la mejora del DS**, en vez del binario actual
"saltar (queda stale) o `--force` (pierde la adaptación)". Es el motor que faltaba para que, cuando un elemento
de diseño común cambie, se pueda distribuir a los satélites de forma segura sin destruir su personalización.

Inserta una **3ª vía** en el arm `isAdapted` de `copyInto` (cli.mjs:96), detrás de un flag **opt-in `--merge`**
(el `update` plano mantiene el contrato exacto de ECO-144: SKIP + exit 3), que corre una **fusión a 3 bandas
`git merge-file --diff3`** con:
- **base** = la versión del DS de la que salió la copia (el SHA que E4a ya fija por fichero en el manifest),
- **theirs** = la copia adaptada del consumidor,
- **ours** = la fuente actual del DS.

Pull-only (corre dentro del `em-ui update --dest` del propio consumidor; ningún push central), minimal-forward
(reusa el verbo `pin` de E4a + el gate de conflictos de E4c en vez de inventar `adopt`/`--continue`), y diseñado
explícitamente contra los 5 modos de fallo que ECO-144 listó.

**Sinergia con E4c:** en conflicto real, `git merge-file` escribe marcadores estándar y la máquina sale ≠0; el
gate **`Conflict markers`** (ahora REQUIRED, ECO-157) **bloquea el merge a main** → un reconcile con conflicto es
un PR rojo deliberadamente no-mergeable que un humano resuelve. E4c es el backstop que hace segura esta máquina.

**Estado del fleet hoy:** las 77 entradas de los 2 consumidores tienen `entry.sha == blobSha(DS actual)` → ningún
caso "adaptado-con-base-avanzada" existe todavía (el DS no ha movido esas copias). La máquina es **preventiva**:
protege las 4 adaptaciones del satélite para el momento en que el DS toque uno de esos componentes. El caso real
lo construye el test de referencia.

## Decisiones fijadas

- **Bytes de la base — almacén de bases por-consumidor** (el fork central): el manifest guarda el SHA, no los
  bytes; `git cat-file` NO es fiable (`pin` puede fijar la base a bytes del DS sin commitear). Solución: un
  **store content-addressed** en `<consumer>/.em-ui/base/<sha>` (bytes crudos, key = git blob sha → round-trip
  con `hash-object`, auto-dedup dentro del consumidor, monorepo-independiente). Se persiste en `recordEntry`
  **SOLO para copias `@em-ui-adapted`** — las únicas que pueden ir a un merge a 3 bandas; las no-adaptadas tienen
  base==DS (materializeBase las recupera del DS) → no se duplica la fuente (hoy 4 ficheros del satélite, 0 del
  dashboard, vs 77 si se guardara todo). `materializeBase(sha, destSrc)`: (1) store → (2) si `blobSha(fuente DS)===sha`, la
  fuente del DS (fallback para base-aún-actual) → (3) si falla, **REHÚSA y degrada a SKIP+exit-3** (nunca adivina
  base, nunca 2-way silencioso). SIN fast-path `cat-file` y SIN GC (over-engineering a esta escala; recortados
  por el crítico). El path `.em-ui/base/` va FUERA de los árboles que escanean check-conflict-markers y
  check-component-drift (escanean por extensión de código bajo `src/`; los blobs sha-named no tienen extensión).
- **Migración de los 2 manifests existentes:** hoy las 77 entradas son recuperables (`entry.sha == DS actual`) →
  el backfill escribe los bytes de la fuente DS al store. El código maneja el caso general (si `entry.sha != DS`
  y no hay bytes → grandfather con WARNING, no hard-fail; re-pin al DS actual como opción del operador).
- **Opt-in `--merge`:** el `update` plano NO cambia (contrato ECO-144). La máquina solo actúa con el flag.
- **Clean merge (exit 0):** guarda bytes fusionados, `recordEntry` AVANZA la base al SHA nuevo del DS (preserva
  `hold` + la cabecera `@em-ui-adapted`) → idempotente en re-runs.
- **Conflicto (exit>0):** marcadores in-place en la copia, NO avanza base, sale ≠0, imprime el fichero. La
  resolución reusa músculo existente: humano quita marcadores → `em-ui pin <file>` (re-fija base); abort =
  `git checkout -- <file>`; adoptar DS = `--force`. CERO verbos nuevos.
- **Resultado ESTRUCTURADO por-fichero** (console-ready, [[eco-propagation-operating-model]]): la máquina emite
  un resultado máquina-legible (clean/conflict/skipped/stale por fichero) que una consola de aprobación futura
  pueda leer — sin construir la consola (diferida hasta conectividad con el cliente).

## Acceptance Criteria

- `em-ui update <C> --dest <src> --merge` sobre un fichero `@em-ui-adapted` cuya base del DS AVANZÓ hace una
  fusión a 3 bandas: **conserva la adaptación Y aplica el delta del DS** (0 conflictos → escribe el merge y avanza
  la base). El `update` SIN `--merge` mantiene el contrato de ECO-144 (SKIP + exit 3) sin cambios.
- **Test de referencia (ADR-028:52), OBLIGATORIO:** reproducir sat-cristian-garcia Button.tsx — `copyFileSync`
  destruiría la adaptación, pero `--merge` base-pinned la preserva y aplica el update del DS con 0 conflictos.
- En **conflicto** real: deja marcadores estándar en la copia, NO avanza la base, sale ≠0. El gate `Conflict
  markers` (required) impide que lleguen a main.
- **Base irrecuperable** (no en store y `blobSha(DS)!=sha`): REHÚSA el merge y degrada a SKIP+exit-3 — nunca
  clobbea, nunca adivina una base.
- Los **5 modos de ECO-144** cubiertos: base podada→rehúsa; markers anidados al re-run→pre-check
  `hasConflictMarkers(mine)` aborta; STALE (`blobSha(mine)==entry.sha`)→catch-up sin merge; markers no llegan a
  main→gate required+exit≠0+base temp en scratch; monorepo→store repo-independiente.
- El **store** (`.em-ui/base/<sha>`) se puebla en `recordEntry` **solo para copias adaptadas**; `check-manifest`
  avisa (soft) si una base no es materializable; el path
  está excluido de check-conflict-markers y check-component-drift. Los 2 consumidores existentes shippean su
  store (backfill).
- `hold` sigue precediendo el arm (un fichero congelado no se toca). La máquina es **pull-only** (corre en el
  árbol del consumidor vía `--dest`; ningún push).
- **Ships con test de integración** (design-system/tests/) que ejercita clean-merge + idempotencia + conflicto +
  base-irrecuperable + STALE fast-forward + hold-frozen.

## Alignment

Implementa/toca estas decisiones del norte de `design-propagation` (ADR-028):

- **Reconcile base-pinned (build-now item 1)**: es exactamente esta pieza — el 3-way `git merge-file` sobre el SHA
  base que E4a fija, que conserva la divergencia declarada del consumidor al propagar.
- **Invariante PULL (hard, ADR-006/007/027)**: corre en el árbol propio del consumidor vía `--dest`; ningún actor
  central escribe bytes. El store es local al consumidor.
- **2 clases de error (crudo grep-catchable vs semántico)**: la máquina resuelve/superficializa solo conflictos
  TEXTUALES/estructurales (git merge-file); lo semántico (token válido pero equivocado) es revisión de diseño +
  gates de censo, NO el merge.
- **Sinergia con E4a/E4b/E4c**: consume el SHA base de E4a; el resultado estructurado alimenta al reporter de E4b
  y a la consola futura; el gate de conflictos required de E4c es el backstop de seguridad.
- **No-goals respetados**: no hay push central, no auto-remedia (observa/fusiona/rehúsa, nunca reescribe una
  adaptación bloqueada — locked = SKIP+report), no markers @brand por-elemento, no allow-lists, no DTCG, no
  re-platform a npm, no verbos adopt/--continue/abort.
