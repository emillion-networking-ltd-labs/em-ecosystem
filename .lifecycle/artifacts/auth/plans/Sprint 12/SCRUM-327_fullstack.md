## Shared Architecture Context

### Goal
Close 4 live re-authentication gaps surfaced by the SCRUM-327 enrichment audit by requiring password confirmation on sensitive Profile actions:

1. `POST /auth/trusted-devices` (Trust device) — currently no re-auth (FAIL)
2. `DELETE /auth/trusted-devices` (Revoke all) — currently no re-auth (FAIL)
3. `DELETE /auth/trusted-devices/:id` (Revoke one) — currently no re-auth (FAIL)
4. `POST /auth/passkeys/register/options` + `register/verify` — currently no re-auth (FAIL)
5. `DELETE /auth/passkeys/:id` — partial (optional password). Make password mandatory whenever the user has `passwordHash` set (WARN → PASS).

MFA disable, recovery-code regeneration, and idle-session timeout are already PASS — out of scope.

### Standards reference
OWASP ASVS V2.8 (Authentication: Re-authentication for high-risk transactions), NIST SP 800-63B §5.2, GitHub/Google/Stripe sudo-mode convention.

### API contract (cross-cutting)
Each sensitive backend endpoint accepts a body with a `password` field (string, non-empty). On success: 200/201 as today. On missing password: `400 Bad Request` with `ErrorMessages.user.PASSWORD_REQUIRED`. On wrong password: `401 Unauthorized` with `ErrorMessages.user.INVALID_PASSWORD`. On OAuth-only user (no `passwordHash`): `400 Bad Request` with `ErrorMessages.mfa.PASSWORD_REQUIRED_NO_PASSWORD` (mirrors `mfa.service.disableMfa` precedent).

### Design decisions taken (flagged for /develop confirmation)

These choices diverge from the literal text of the enriched ticket and follow established codebase conventions instead. They are recorded here so that during `/develop` the user can override before any code is written.

- **D1 — DTO field name `password` (not `currentPassword`)**. Rationale: existing `MfaDisableDto` uses `password!: string` (not `currentPassword`). Consistency beats the suggestion in the ticket. **Override path**: rename the field in all 5 DTOs and propagate through 6 service signatures + 6 controller bodies + 2 frontend hooks + 2 API helpers if user prefers `currentPassword`.

- **D2 — OAuth-only users: throw 400, no MFA-TOTP fallback in this ticket**. Rationale: the existing `mfa.service.disableMfa` and `regenerateRecoveryCodes` both throw `BadRequestException(PASSWORD_REQUIRED_NO_PASSWORD)` when `!user.passwordHash`. There is no MFA fallback today for the analogous flows. Adding one only here creates inconsistency. The ticket itself flags the broader gap as Risk #2 — a follow-up ticket can require either a password OR MFA on accounts with passkeys/trusted devices. AC5 of the ticket is therefore **scoped down** to: OAuth-only users get a 400 with the existing `PASSWORD_REQUIRED_NO_PASSWORD` message; UI surfaces this as a toast directing them to set a password first. **Override path**: implement MFA-TOTP fallback in this ticket — adds ~80 LOC across `passkey.service` + `trusted-device.service` (TOTP verify branch + Crypto/Mfa service injections) and 3 new test cases per service (~12 tests total). Also retroactively add the same fallback to `mfa.service.disableMfa` for parity.

- **D3 — No new `*_REAUTH_SUCCESS/FAILURE` audit enums**. Rationale: the existing `DEVICE_TRUSTED`, `DEVICE_UNTRUSTED`, `PASSKEY_REGISTERED`, `PASSKEY_DELETED` events already log on the success path. Failed password attempts on these endpoints throw `Unauthorized` and are already covered by the rate-limiting layer (`AUTH_RATE_LIMITS`); duplicating them with new audit enums adds maintenance cost without an SOC 2 / ASVS check that demands them. **Override path**: add 4 new enum values (`TRUST_DEVICE_REAUTH_FAILURE`, `PASSKEY_REGISTER_REAUTH_FAILURE`, plus matching `_SUCCESS` if symmetry desired) in `audit-action.enum.ts`, log inside the service `catch (UnauthorizedException)` branch, update audit-action documentation in `data-model.md`, add 4 spec assertions.

- **D4 — `register/options` becomes the password-protected gate; `register/verify` does NOT re-check password**. Rationale: the WebAuthn challenge is short-lived (`WEBAUTHN_CHALLENGE_TTL_SECONDS`) and is only issued AFTER password verification. Re-verifying on `register/verify` would force the user to re-type the password mid-biometric prompt. AC3 already specifies this exact semantic. **Override path**: add password to BOTH endpoints if defense-in-depth is desired, with the trade-off of UX friction.

- **D5 — Branch off the `feature/SCRUM-347-backend` working tree**. Rationale: Camino Total ordering in `MEMORY.md` puts the `commit` cycle for SCRUM-347/348/327/349/350 at phase F, after all four /develop cycles. SCRUM-347 changes (Redis deny-list + jwt-payload `sessionId`) are pre-requisites for AC10 (Phase 3 audit re-run must show 0 FAIL with re-auth + immediate-revoke both shipping). **Override path**: branch from clean `main` and rebase onto SCRUM-347 before /verify.
